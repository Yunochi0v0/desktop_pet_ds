# DECISIONS.md — 重要决定记录

> 为什么这样决定：决定 + 原因 + 当时的取舍。
> 答辩时这份文件比代码本身更能说明「是你做的决定，不是 AI 替你做的」。

---

## D1 · 采用「全屏透明窗口 + CSS 定位小球」，而不是「小窗口跟随鼠标移动」

- **决定**：窗口铺满整个工作区，球体只在窗口内部用 CSS 移动。
- **原因**：Phase 2 要弹气泡对话框，需要一个足够大的画布。如果窗口只有 96×96，
  后面每次弹窗都得动态改窗口尺寸和位置，复杂度和 bug 面会成倍增加。
- **取舍**：代价是多了一个全屏窗口常驻在桌面层。但这个窗口是鼠标穿透的，
  对桌面操作零干扰（这也是 Phase 1 要重点验收 A4 的原因）。

## D2 · 鼠标穿透用「主进程默认穿透 + 渲染进程命中检测」的方案

- **决定**：主进程一开始就 `setIgnoreMouseEvents(true, { forward: true })`；
  渲染进程监听 `mousemove` 判断指针是否在球上，再通过 IPC 切换。
- **原因**：这是 Electron 官方支持且唯一稳定的做法。关键在 `forward: true` ——
  它让窗口在穿透状态下仍然能收到鼠标移动事件，否则渲染进程根本无从判断。
- **取舍**：每次鼠标移动都会做一次命中判定（几乎零成本），
  并通过「状态没变就不发 IPC」来避免 IPC 洪泛。

## D3 · 拖拽层与动画层拆成两级 DOM

- **决定**：`#pet` 只做 `translate3d(x, y, 0)`；`.pet-core` 只做 `translateY` 呼吸动画。
- **原因**：两者都用 `transform`，写在同一个元素上会互相覆盖 ——
  呼吸动画会把拖拽坐标"吃掉"，表现为球体怎么拖都不动。
- **取舍**：多一层 div，换来两个关注点互不干扰。

## D4 · 引入 `preload.js`（用户原始需求中没有提到）

- **决定**：不直接在渲染进程用 `require('electron')`，而是用
  `contextBridge` 暴露 3 个白名单方法。
- **原因**：Electron 官方安全基线要求 `contextIsolation: true` +
  `nodeIntegration: false`。直接开 `nodeIntegration` 会让渲染进程拥有
  完整 Node 权限，一旦 Phase 3 接入网络内容就是明显风险。
- **取舍**：多写一个文件、多一层间接调用。收益是 Phase 3 处理 API Key 时，
  可以自然地坚持"密钥只留在主进程"这条原则。

## D5 · 不做❝鼠标悬停才显示❞的隐藏逻辑，球体始终可见

- **决定**：桌宠永远显示，只通过透明度和发光强度区分「可交互 / 不可交互」。
- **原因**：桌宠的价值在于"存在感"，而不是又一个要去找的隐藏窗口。
- **取舍**：需要接受它一直在视觉上存在（因此待机动画刻意做得很轻）。

## D6 · 使用 Git checkpoint 管理每一次阶段成果

- **决定**：Phase 1 验收通过后立刻 commit 一次，之后再开始 Phase 2。
- **原因**：课程要求「Never let AI make large changes without a way back」。
  下一步 Phase 2 要改动 main.js 与 renderer.js，一旦出问题可以直接回退到
  Phase 1 这个已经验收过的状态。

## D7 · API Key 改存渲染进程的 localStorage（**推翻 D4 的一半**）

- **决定**：`localStorage['deepseek_api_key']`，由使用者在设置页自己填（BYOK）。
- **为什么推翻 D4**：D4 当时写的是「密钥只留在主进程」。真做起来发现，
  这个项目**没有后端服务器**，key 是使用者自己的（BYOK），
  主进程保存反而要额外引入本地文件 / 环境变量 / 加密方案，
  最后仍然要落到磁盘上某处 —— 安全性没有本质提升，复杂度却上去了。
- **取舍**：key 会以明文待在本机 localStorage 里，渲染进程可读。
  可接受，因为：设备是使用者自己的、key 是使用者自己的、不进 Git、
  日志只输出「是否已配置」的布尔值，永不打印 key 本身。
- **什么时候必须改回来**：一旦引入后端（由服务端持 key、前端只发问题），
  或要把应用分发给第三方使用时，必须重新走「密钥不进客户端」的路线。

## D8 · 渲染进程直接 fetch DeepSeek，不做主进程代理

- **决定**：`renderer.js` 里直接 `fetch('https://api.deepseek.com/chat/completions')`。
- **原因**：动手前先用 curl 带 `Origin: null` 实测过对方接口 ——
  `access-control-allow-origin` 回 `null`（`file://` 页面的 Origin 恰好也是 `null`），
  预检放行 `authorization, content-type` 和 `POST`。
  既然浏览器层面本来就允许，写主进程代理就是纯粹的多余劳动。
- **取舍**：多写一层代理要多加 IPC 通道，而且**必须把 key 交给主进程**，
  反而把密钥暴露面从「一个进程」扩大到「两个进程」。
  代价是依赖对方不收紧 CORS —— 万一哪天收紧了，
  改动面被刻意控制在一处：`requestDeepSeek()` 一个函数
  （它是唯一碰网络的函数），换成 IPC 调用即可。

## D9 · 「思考中」只用 CSS 动画，绝不做差分图

- **决定**：思考状态 = `.pet-sprite.thinking` 轻微摇摆 + `.pet-core::before` 光晕呼吸
  + `body.thinking` 氛围微调，**始终是同一张立绘**。
- **原因**：两条约束叠在一起 ——
  ① 项目**只有一张**立绘资源，「换个表情」没有素材可用；
  ② 桌宠走的是浅色 DeepSeek 风格，霓虹 / 扫描线 / 故障感会直接跟它打架。
- **取舍**：表现力确实不如多张差分图丰富，只能靠「轻微摇摆 + 呼吸光晕」表达思考感。
  好消息是它天然满足可访问性：`prefers-reduced-motion: reduce` 时关掉动画即可，
  不需要另做一套静态素材。
- ⚠️ **2026-10-22 更新：本条的依据（「只有一张图」）已不成立，差分逻辑见 D10。**
  但「不用霓虹 / 扫描线」的风格结论、以及「思考动画只加类名」的做法继续有效。

## D10 · 立绘差分：三档「思考深度」↔ 三张图（**部分推翻 D9**）

- **背景**：用户追加需求 —— 设置里的「思考深度」（低 / 中 / 高）要对应三张不同比例的
  角色立绘；切换后立绘**立刻**换、下次启动**还记得**；三张图用固定文件名，
  以后拿到成品图直接覆盖即可，不改代码。
- **决定**：
  1. 图片路径固定为 `assets/pet-low.png` / `assets/pet-high.png` / `assets/pet-max.png`，
     映射表在 `renderer.js` 的 `DEPTHS`，**换图 = 覆盖同名文件**；
  2. 画框随档位变：`192×192` / `210×280` / `240×360`（由 `--pet-w` / `--pet-h` 驱动），
     原来是单值 `state.size`，现重构为 `state.box {w,h}` ——
     命中判定、拖拽边界、气泡定位、尾巴偏移全部改成按矩形算；
  3. 下拉框 `change` 即生效、即写入 `localStorage['pet_thinking_depth']`，
     **不再额外点「保存」**；「保存」按钮仍然只管 API Key；
  4. 思考动画继续只加 `.thinking` 类名（D9 的核心做法保留），
     换 `src` 不碰类名，所以思考中换档动画不会断。
- **为什么推翻 D9 的一半**：D9 的论据是「项目只有一张立绘」。现在有差分图了，
  这个事实前提消失。但 D9 里「光效用淡蓝微光、不要霓虹/故障感」的风格结论仍然有效，
  所以是**部分**推翻，不是全盘重来。
- **代价 / 新约束**：
  - 多一个持久化键，需要在「存不住」时诚实降级（localStorage 不可用 → 只换图、不报成功）；
  - 画框不再是正方形，所有几何计算都必须宽高分开（写死 192 的地方会立刻错位）；
  - `scale(1.1)` 的溢出量随画框变大（360 高时单侧约 18px），贴边 margin 必须大于它；
  - 建议立绘**紧裁到 alpha 边界**：方形图塞进竖画框时，`object-fit: contain` 会留白，
    CSS 已用 `object-position: 50% 100%` 让图贴住画框底部（否则角色会浮在投影上方）。
- **保留**：`assets/pet-character.png` 不删，作为原始素材备份；页面已不再引用它。

## D11 · 「思考深度」用换模型实现，而不是假装有 `reasoning_effort`

- **背景**：用户问「轻量/标准能不能影响 AI 的思考」，并明确要求真的做出来。
  之前 Phase 3.5 的下拉框只换立绘，请求里永远 `deepseek-chat` —— 那是**装饰**。
- **事实前提**：DeepSeek 的 Chat Completions **没有** `reasoning_effort` 这类参数
  （那是 OpenAI 的 o 系列）。于是只有三种可选杠杆：
  ① 换模型（`deepseek-chat` ↔ `deepseek-reasoner`）；
  ② 换 `max_tokens` / `temperature`；
  ③ 用 system 追加「要答多细」的要求。
- **决定**：三条一起用，按档位组合：
  - 轻量 = chat + 600 tokens + 0.6 + 「三句话内」；
  - 标准 = chat + 1600 tokens + 0.35 + 「结论 + 要点」；
  - 极致 = **reasoner** + 16000 tokens + 不带 temperature + 展示 `reasoning_content`。
- **为什么极致必须去掉 temperature**：reasoner 不接受采样参数，带了直接 400。
  这属于「参数存在性」问题，不能靠 try/catch 兜底，必须在拼请求时就不发。
- **为什么把推理过程折叠展示**：这是「深度真的生效」最直接的证据 ——
  用户能读到模型在想什么，而不是被告知「我们在深度思考」。
  默认收起是因为推理动辄上千字，铺开会把回答挤出视口。
- **代价（必须对用户讲清）**：
  1. 极致档**更慢更贵**，推理 token 也计费；等待上限放宽到 180 秒；
  2. 三档的「思考」差异本质是「模型不同」，不是同一模型的思考档位 —— 别把它说成
     「同一个模型想得更久」，那是错误的描述；
  3. 推理过程**不进入历史**（回传 `reasoning_content` 会让 reasoner 400），
     多轮追问时模型只看到自己上一轮的结论。
- **被推翻的东西**：Phase 3.5 里「下拉框只影响外观」的隐含定位被改成「外观 + 请求」，
  `index.html` 的注释与状态行文案同步改口径（状态行现在会写当前模型）。

## D12 · 换档的「变身」用暗场换图，不押在动画上

- **背景**：三档立绘换成完全不同的画风（半身 / 戴饭盆的 Q 版 / 九头身），
  切档时直接换 `src` 会「啪」地跳一下，像网页换图，不像桌宠变身。
- **候选方案**：
  1. 交叉淡入（两张图叠着渐变）—— 画风差异大时会出现「两个头重叠」的鬼影；
  2. 缩放弹跳 + 直接换图 —— 换图那一帧仍然硬切；
  3. **先收起 → 暗场换图 → 再弹出**（选中）。
- **决定**：`.pet-core` 在 170ms 内缩到 0.94/0.89、下沉 7px、淡出；
  完全看不见的那一刻换 `src` + 换画框 + 重摆脚底；再用 330ms 从下方弹回
  （`translateY(11px) → 0`，带 1.025 的轻微过冲）。总时长 0.5s。
  ——**已被 D13 取代**：节奏放慢到 0.84s，并改为「旧图上浮退场 → 新图淡入」；
  这里保留原文是为了留下当时的取舍理由。
- **为什么动画挂在 `.pet-core` 上**：`<img>` 自己的呼吸/摇摆动画都在 `transform` 上，
  再往同一个元素写 `transform` 会互相覆盖。`.pet-core` 是外层容器，正好是「整体动作」的层。
- **为什么暗场才换框**：若先换画框再换图，旧角色会被新画框拉变形（`object-fit: contain`
  下比例突变），看起来像贴图错误。把两件事放进同一帧，用户只会看到「变身」。
- **正确性不押在动画上**：窗口被遮挡/最小化时 Chromium 会暂停渲染帧，WAAPI 的
  `finished` 可能永不 resolve。所以每段动画都有 `duration + 160ms` 的定时兜底，
  先到就先继续，并 `cancel()` 掉没播完的动画，避免立绘停在半透明中间帧。
- **降级**：`prefers-reduced-motion: reduce` 或环境没有 WAAPI 时，直接换图（0 动画）。
  启动时恢复上次档位也不播动画，否则一开屏角色先消失一下。
- **不变量**：动画期间 `state.depth` 已经切好 → 请求参数、localStorage 立刻生效；
  只有「画面 + 画框」延后到暗场。这样用户切完就退出，记忆也不会丢。

## D13 · 变身改为「旧图退场 → 新图淡入」，并把总时长放到 0.84s

- **背景**：D12 的版本是 170ms 收起 + 330ms 弹出，中间在暗场换图。实测（逐帧+逐 50ms 采样）
  读起来偏快，像「眨了一下眼」，不太像变身；而且旧图是「原地缩小消失」，
  新图是「从下方弹出」，两个动作的方向感不统一。
- **用户要求**：延长动画时间；旧立绘单独退场，新立绘淡入。
- **决定**：
  - 退场 380ms：旧图 `opacity 1 → 0`，同时 `translateY(0 → -8px)`、`scale 1 → 0.97`
    （向上飘走，和「离开」的方向一致）；
  - 入场 460ms：新图 `opacity 0 → 1`（35% 处到 0.55），`translateY(10px → 0)`、`scale 0.985 → 1`；
  - 两段各自完整播完，中间只有一帧换图；光晕扩散延长到 900ms 盖住整个动作。
- **为什么不用交叉淡入**：两档画风差异大，重叠会有「两张脸互相穿透」的鬼影，
  且两档画框尺寸不同（192² / 210×280 / 240×360），重叠那一段旧图会被新画框拉变形。
- **换图时机**：必须等旧图真正淡到 0 再换 `src`。实现上换图发生在旧图动画
  `fill: forwards`（opacity 0）还压着的时候，新图动画建好之后才 `cancel()` 旧动画 ——
  否则 cancel 会先恢复不透明，露出一帧旧图。
- **可测性**：`measure-morph.js` 每 50ms 采样 `getComputedStyle(.pet-core).opacity`，
  实测 1.00 → 0.05（380ms）→ 换图 → 0.25 → 1.00（840ms），没有空窗、没有回闪。

## D14 · 人设改为用户提供的「鲸鱼娘」正式版，逐字使用

- **背景**：3.0 阶段为了先跑通链路，`SYSTEM_PROMPT` 放的是占位版（猫耳女仆、自称「大肥鱼」、
  要求 Markdown 排版）。用户现在给了正式人设，并明确「直接使用这段文本，无需修改」。
- **决定**：整体替换为该段文本，**一个字不改**（含标点、全角引号、emoji 式括号动作词、
  空行结构）。模板字符串里的换行就是发给模型的原样换行，因此禁止自动重排/折行。
- **为什么不压缩成一段**：这段文本本身用「【核心性格】/【对话风格】/【场景反应示例】」
  分段，模型对分段指令的遵循度明显更好；压成一段等于改写，违背用户要求。
- **和深度档的关系（保留）**：`buildPayload()` 仍会在人设后面追加
  `【本次回答的详细程度】…`（轻量「从简」/ 标准「周全」/ 极致「先推演」）。
  这是 3.6「思考深度真影响回答」的落地手段，属于**另一层**指令，不是对人设的改写。
  若两者冲突（人设要求 2–3 句，极致档要求给步骤），以人设为语气、以尾注为信息量。
- **防回归**：测试断言人设签名（`你是 DeepSeek 鲸鱼娘`、`白米饭是你的神圣底线`、
  `信不信我用尾巴抽你`）、断言不再出现 `猫耳女仆`、断言长度 ≥ 751 字。
- **不改的文案**：`NO_KEY_MESSAGE`（「要先给大肥鱼买白饭吃的饭卡」）是需求指定的原话，
  虽然和新设定里「讨厌被叫大肥鱼」有戏剧性反差，但它是错误提示而非人设，保持原样。

## D15 · 输入法候选词被挡：降窗口层级，而不是改 CSS

- **现象**：在气泡输入框里打字，macOS 输入法的候选词面板看不见（或只露出一条边），
  像是被气泡/窗口裁掉。
- **排除的假设**：
  1. `overflow: hidden` —— 候选词面板是**系统窗口**，不是 DOM，CSS 裁不到它；
  2. 输入框太靠下 —— 输入框距屏幕底边仍有 250px 以上，放得下一整块候选词；
  3. 窗口不可聚焦 —— `focusable` 本来就是 true，否则连字都打不进去。
- **真实原因**：桌宠窗口被抬到了 `'screen-saver'` 层级（为了盖住全屏应用，
  见 Phase 1 验收项），而输入法候选词面板的窗口层级只在「弹出菜单」那一档，
  于是整块面板被这块**透明全屏窗口**盖住了 —— 视觉上就像「被对话框挡住」。
- **决定**：输入框 `focus` 时把窗口降到普通层级（`setAlwaysOnTop(false)`），
  `blur` / 收气泡 / 窗口失焦时恢复 `setAlwaysOnTop(true, 'screen-saver')`。
  只用一个布尔 IPC `pet:set-ime-friendly`，不暴露任意窗口参数。
- **为什么不干脆永久用普通层级**：Phase 1 要求「盖住全屏应用」，
  永久降级会让桌宠被别的窗口压住，等于回退验收项。
- **为什么不用 CSS `padding-bottom` 兜底**：那只是在「插入点位置」上做微调，
  治不了层级问题；但仍给气泡底部留了 4px 呼吸位（12px → 上下不对称），
  并显式写 `overflow: visible`，防止将来有人加裁剪。
- **副作用与兜底**：打字期间桌宠不再置顶（被别的窗口盖住是正常的，
  因为用户正在这个窗口里输入）；`main.js` 的 `win.on('blur')` 再兜一层，
  即使渲染进程没发信号也会恢复置顶。

## D16 · 记忆只存 role/content，好感度独立存储且「只涨不因清空回退」

- **存什么**：`localStorage['chat_history']` 只放 `{role:'user'|'assistant', content:string}`，
  不存 HTML、不存渲染后的节点、不存时间戳。理由：渲染是「不可信输入 → 转义 → 白名单
  Markdown」的一次性过程，把渲染结果存回去等于绕过转义链；时间戳现在没用，存了只是噪音。
- **存多少 / 发多少**：本地留 40 条（20 轮），发给模型只取最近 10 条（5 轮）。
  两者分开是为了「翻得回去」但「不把 token 烧在旧话题上」。
- **为什么不用 `state.messages` 直接当 history**：气泡日志里有 notice / error 这类
  非对话节点，它们不该进上下文；单独维护 `state.history` 才能保证「只把真正的问答带给模型」。
- **好感度为什么单独一个键**：好感度是「关系进度」，不是聊天记录。清空记忆时
  `favor` 必须保留（否则用户一清空就从 50 重来，等于惩罚整理记录的人）。
- **何时 +1**：~~只有拿到正文才 +1~~ —— 该规则已被 **D18** 取代（现在按关键词 ±10/-1，发送前结算）。
  请求体里用的是「涨之前」的值，所以第一轮发 50、第二轮发 51 —— 语义是
  「这一轮开始时她对你的好感」，不是「聊完之后的结算」。
- **注入位置**：`SYSTEM_PROMPT` → 好感度块 → 深度尾注。人设定语气，好感度微调语气，
  深度定信息量；顺序固定，测试断言 `favorAfterPersona` 为真。

## D17 · 吸附用一次性 CSS 过渡；托盘图标必须被模块级变量持有

- **吸附为什么不用 rAF 自己写缓动**：`transform` 已经走合成线程，CSS `transition`
  同样在合成线程上跑，不占主线程；自己写还要处理「动画中途又开始拖拽」的中断。
  实现上只在 `mouseup` 且 `wasDrag` 为真时加 `.snapping`（260ms），
  动画结束就摘掉 —— 平时拖拽仍是 0 延迟跟手。
- **为什么只在松手时吸附**：拖动过程中贴边会「粘住」，想放到边上一点点的位置反而做不到；
  松手才吸附符合「整理桌面」的直觉。单击（没拖动）不吸附，避免点一下球就跳走。
- **减弱动态效果**：`matchMedia('(prefers-reduced-motion: reduce)')` 命中时直接改坐标、
  不加过渡类；和变身动画的处理保持一致。
- **托盘为什么要存 `tray` 引用**：Electron 的 `Tray` 一旦没有 JS 引用就会被 GC，
  图标随之消失（macOS 上表现为托盘图标闪一下就没）。所以放模块级变量，
  并在 `before-quit` 里 `destroy()`，避免退出时残留。
- **图标规格**：源图 `src/assets/icon.png` 64×64，`nativeImage.resize({width:18,height:18})`
  适配菜单栏；不直接用 662×788 的立绘（菜单栏会糊成一团）。

## D18 · 好感度养成化：数值只活在后台，结算放在发送前

- **界面零暴露**：设置页从 `记忆 N 条 · 好感度 M/100` 改成只显示 `记忆 N 条`。
  不留进度条、不留 tooltip 数字。理由：一旦用户看见数值，就会开始「算性价比」，
  对话会变成刷分；隐藏之后，语气变化才是唯一反馈。
- **结算时机 = 发送前**，而不是回答成功后。原因有三：
  1. 需求明确要求「发送对话前先匹配」；
  2. 本轮 system 能立刻用上结算后的档位，语气和这一句话对得上；
  3. 回答成功后再改，会让「这一轮她为什么突然变凶」滞后一轮，读起来很怪。
- **失败不退还**：先讨好再断网取消，如果退还就能反复刷。代价是网络差时可能白掉 1 点，
  但数值范围只有 0–100、单次幅度最多 10，这个误差可以接受。
- **一句话只加一次**：多个讨好词命中仍然 +10。否则「白米饭红烧肉辛苦了投喂大肥鱼真棒」
  一句话直接 +50，养成曲线当场崩掉。
- **分档用左闭右开**：`<30 / [30,60) / [60,85) / ≥85`。默认 50 落在「日常嫌弃」，
  这是故意的 —— 一上来就傲娇会显得人设没落地，先嫌弃再软化才有养成感。
- **注入内容包含真实数值**：模型需要它来判断档位边界，但同一段里明确命令
  「不要提到好感度、数值、档位」。数值可以给模型看，不能给用户看。
- **关键词用 `includes` 而不是正则**：中文没有词边界，正则 `\b` 不适用；
  词表只有五个，`includes` 更好读、更好加词，也不会因为用户多打空格就漏。

## D19 · 右键查余额：复用同一个气泡的第三个视图，只读、不落盘

- **为什么复用 `#bubble` 再加 `#view-wallet`**：需求要「弹出原有的对话气泡」。
  另开一个窗口/浮层会引入第二套定位、第二套穿透判定和第二套定位逻辑，
  还可能和拖拽、吸附抢层级；复用同一个气泡只多一个 `hidden` 视图，
  `positionBubble()` / `relayoutBubble()` 全部照旧生效。
- **为什么右键只查余额，不做菜单**：桌宠上没有第二个值得放进右键菜单的动作，
  弹一个只有一项的菜单反而多一次点击。右键 = 查询，是这类桌宠的常见约定。
- **`contextmenu` 必须 `preventDefault()`**：Electron 在 macOS 上会弹系统菜单
  （「重新载入 / 检查元素」那一套），盖在透明桌宠上非常出戏。
  同时 `stopPropagation()`，避免以后有人给 `window` 加右键逻辑时重复触发。
- **为什么不在 `mousedown` 里判右键**：`onMouseDown` 已经用 `button !== 0` 直接返回，
  右键不会进入拖拽状态机；用独立的 `contextmenu` 事件语义更准，
  也不会被 `DRAG_THRESHOLD` 之类的阈值影响。
- **加载态停留 >5 秒也不自动收**：需求要求「不要几秒后自动消失」。这里干脆没有任何
  自动关闭定时器 —— 气泡什么时候收，只由左键、ESC、窗口失焦决定。
  唯一的定时器是 10 秒请求超时，它只负责把「翻找钱包中」换成报错文案。
- **左键语义**：钱包开着时左键点球 = 切回聊天（不关气泡），因为这时用户最可能想打字；
  关掉气泡时 `resetWalletView()` 静默退回聊天，下次打开不会残留钱包视图。
- **连点右键用 `balanceSeq` 防串台**：两次请求谁先回来不确定，旧结果绝不能覆盖新结果；
  序号变了或用户已经切走（`state.panel !== 'wallet'`）就直接丢弃。
- **余额接口只读**：不写 `chat_history`、不动 `favor`、不追加聊天气泡。
  「查余额」不是对话，把它写进记忆只会污染上下文。
- **币种不硬猜**：只给 CNY/USD 配符号，其它币种原样显示 `金额 代码`，
  避免把 EUR 显示成 ¥。
